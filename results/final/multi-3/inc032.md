# Incident inc032

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_orders_order_key` fail (1200 rows): Got 1200 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.orders`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_orders`, `stg_orders`

**Evidence**

raw.orders has 16,200 rows but only 15,000 distinct o_orderkey values; many order_key values appear twice with identical column values (e.g., o_orderkey=195). stg_orders simply selects from raw.orders, so duplicates flow downstream, causing unique_stg_orders_order_key to fail with 1,200 duplicate rows. Since duplicates are exact copies, they can be removed by deduplication in the staging model (SELECT DISTINCT) without data loss.

## What was done

Proposed a change to `models/staging/stg_orders.sql`. Added DISTINCT to the SELECT in the staging model to remove exact duplicate rows that appear in raw.orders. The duplicates are identical across all columns, so deduplication does not lose any unique information. This resolves the unique_stg_orders_order_key check failure while preserving column names and types.

```diff
--- a/models/staging/stg_orders.sql
+++ b/models/staging/stg_orders.sql
@@ -1,4 +1,4 @@
-select
+select distinct
     o_orderkey as order_key,
     o_custkey as customer_key,
     o_orderstatus as order_status,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix correctly deduplicates exact duplicate rows from the source, addressing the upstream duplicate issue without masking data or altering logic. No type/format changes involved.
