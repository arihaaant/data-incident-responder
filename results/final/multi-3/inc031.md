# Incident inc031

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_orders_order_key` fail (300 rows): Got 300 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.orders`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_orders`, `stg_orders`

**Evidence**

raw.orders has 15300 rows but only 15000 distinct o_orderkey values, indicating 300 exact duplicate rows (same values across all columns). The staging model stg_orders simply selects o_orderkey as order_key, so duplicates propagate, causing unique_stg_orders_order_key check to fail. Duplicates are identical, so they can be deduplicated in the staging model.

## What was done

Proposed a change to `models/staging/stg_orders.sql`. Added DISTINCT to remove the 300 exact duplicate rows in raw.orders. This preserves the original column names and types while ensuring each order_key appears only once, allowing the unique_stg_orders_order_key check to pass.

```diff
--- a/models/staging/stg_orders.sql
+++ b/models/staging/stg_orders.sql
@@ -1,5 +1,5 @@
 select
-    o_orderkey as order_key,
+    distinct o_orderkey as order_key,
     o_custkey as customer_key,
     o_orderstatus as order_status,
     o_totalprice as total_price,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix removes only exact duplicate rows (identical across all columns) using SELECT DISTINCT, preserving data integrity and satisfying unique check. No type/format changes; profile not required.
