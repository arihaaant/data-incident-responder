# Incident inc038

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_customers_customer_key` fail (225 rows): Got 225 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.customer`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `dim_customers`, `fct_daily_revenue`, `fct_orders`, `stg_customers`

**Evidence**

raw.customer has 1725 rows but only 1500 distinct c_custkey; duplicates (e.g., c_custkey=27) are identical across all columns, causing 225 duplicate customer_key rows in stg_customers, failing unique check.

## What was done

Proposed a change to `models/staging/stg_customers.sql`. The upstream raw.customer source contains exact duplicate rows (same c_custkey and all other column values). This caused 225 duplicate customer_key rows in the stg_customers model, failing the unique check. Since the duplicates are identical across all columns, we can safely deduplicate by selecting distinct rows. Adding `distinct` preserves the original column names and types while removing the duplicate records, allowing the unique check to pass.

```diff
--- a/models/staging/stg_customers.sql
+++ b/models/staging/stg_customers.sql
@@ -1,4 +1,5 @@
 select
+    distinct
     c_custkey as customer_key,
     c_name as customer_name,
     c_address as address,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Exact duplicate rows are removed with DISTINCT, preserving all unique data and fixing the unique key violation without masking non‑duplicate data.
