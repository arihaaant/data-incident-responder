# Incident inc037

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_customers_customer_key` fail (75 rows): Got 75 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.customer`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `dim_customers`, `fct_daily_revenue`, `fct_orders`, `stg_customers`

**Evidence**

raw.customer has 1575 rows but only 1500 distinct c_custkey values, indicating 75 duplicate primary key rows. The duplicate rows are identical across all columns, confirming a duplicated batch. The staging model simply selects columns without deduplication, so the uniqueness check fails on stg_customers.customer_key.

## What was done

Proposed a change to `models/staging/stg_customers.sql`. The raw.customer source contains 75 duplicate rows where the primary key c_custkey is repeated with identical column values. The staging model previously selected rows directly, causing the unique check on customer_key to fail. Since the duplicates are exact copies of a redelivered batch, we can safely deduplicate by using SELECT DISTINCT on all columns. This preserves the original column names and data types while ensuring each customer_key appears only once, allowing the uniqueness test to pass.

```diff
--- a/models/staging/stg_customers.sql
+++ b/models/staging/stg_customers.sql
@@ -1,5 +1,5 @@
 select
-    c_custkey as customer_key,
+    distinct c_custkey as customer_key,
     c_name as customer_name,
     c_address as address,
     c_phone as phone,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix correctly removes the exact duplicate primary key rows by selecting distinct customer_key, addressing the upstream duplicate batch without masking or altering data.
