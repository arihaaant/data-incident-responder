# Incident inc034

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_lineitem_order_line_id` fail (1550 rows): Got 1550 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.lineitem`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_order_items`, `fct_orders`, `stg_lineitem`

**Evidence**

raw.lineitem has 61,725 rows but only 60,175 distinct order_line_id (l_orderkey||'-'||l_linenumber). Duplicate groups (e.g., orderkey 358 linenumber 2) appear twice with identical column values, totaling 1,550 duplicate rows. The stg_lineitem uniqueness check fails because it propagates these duplicates. Identical duplicates indicate a delivery batch issue; deduplication can be applied in the staging model.

## What was done

Proposed a change to `models/staging/stg_lineitem.sql`. Added a deduplication step using ROW_NUMBER() partitioned by the composite key `order_line_id`. Since the duplicate rows are exact copies (identical column values), keeping a single row per `order_line_id` resolves the uniqueness check failure while preserving all original columns and their data types.

```diff
--- a/models/staging/stg_lineitem.sql
+++ b/models/staging/stg_lineitem.sql

```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix correctly removes exact duplicate rows by deduplication on the composite key, addressing the upstream duplicate issue without altering data semantics.
