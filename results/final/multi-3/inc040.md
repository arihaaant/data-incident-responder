# Incident inc040

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_fct_orders_order_key` fail (12900 rows): Got 12900 results, configured to fail if != 0

## Diagnosis

- **Started at:** `model.fct_orders`, column `order_key`
- **Cause:** a change in a model
- **Downstream models affected:** `fct_daily_revenue`

**Evidence**

staging.stg_orders has 15k rows, but marts.fct_orders has 60,175 rows (4x). Duplicate check shows 12,900 duplicate order_key rows. fct_order_items also 60,175 rows, indicating fct_orders joins orders to order_items without aggregation, inflating rows and causing duplicate order_key. The issue originates in the fct_orders model's join logic.

## What was done

Proposed a change to `models/marts/fct_orders.sql`. The duplicate `order_key` rows were caused by the `items` CTE grouping by both `order_key` and `line_number`, which produced one row per line item. By grouping only on `order_key`, we correctly aggregate item metrics per order, ensuring a single row per order when joining back to `stg_orders`. This resolves the unique constraint failure on `order_key` without altering column names or types.

```diff
--- a/models/marts/fct_orders.sql
+++ b/models/marts/fct_orders.sql
@@ -5,7 +5,7 @@
         sum(extended_price) as gross_revenue,
         sum(net_revenue) as net_revenue
     from {{ ref('fct_order_items') }}
-    group by order_key, line_number
+    group by order_key
 )
 
 select
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix correctly aggregates items per order by removing line_number from GROUP BY, eliminating duplicate order_key rows caused by join logic. No masking, no type changes, and addresses root cause.
