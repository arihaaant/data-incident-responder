# Incident inc034

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_lineitem_order_line_id` fail (1550 rows): Got 1550 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.lineitem`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_order_items`, `fct_orders`, `stg_lineitem`

**Evidence**

The unique_stg_lineitem_order_line_id test failed with 1550 duplicate order_line_id values. In raw.lineitem, the combination of l_orderkey and l_linenumber appears multiple times (e.g., orderkey 358 linenumber 2 appears twice) with identical row data, indicating a duplicated batch. Adding DISTINCT to the staging model removes these exact duplicate rows, which resolves the uniqueness test without losing any distinct data.

## What was done

Proposed a change to `models/staging/stg_lineitem.sql`. The unique_stg_lineitem_order_line_id test failed with 1550 duplicate order_line_id values. In raw.lineitem, the combination of l_orderkey and l_linenumber appears multiple times (e.g., orderkey 358 linenumber 2 appears twice) with identical row data, indicating a duplicated batch. Adding DISTINCT to the staging model removes these exact duplicate rows, which resolves the uniqueness test without losing any distinct data.

```diff
--- a/models/staging/stg_lineitem.sql
+++ b/models/staging/stg_lineitem.sql
@@ -1,5 +1,5 @@
 select
-    l_orderkey || '-' || l_linenumber as order_line_id,
+    distinct l_orderkey || '-' || l_linenumber as order_line_id,
     l_orderkey as order_key,
     l_linenumber as line_number,
     l_partkey as part_key,
```
