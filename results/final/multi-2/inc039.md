# Incident inc039

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_parts_part_key` fail (200 rows): Got 200 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.part`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_order_items`, `fct_orders`, `stg_parts`

**Evidence**

raw.part has 2200 rows but only 2000 distinct p_partkey values; duplicate rows exist for many keys (e.g., p_partkey=11 appears twice with identical column values). stg_parts simply selects from raw.part, so duplicates propagate, causing unique_stg_parts_part_key check to fail with 200 duplicate rows. Duplicates are identical across all columns, indicating a delivery duplication, which can be fixed by deduplicating in the staging model.

## What was done

Proposed a change to `models/staging/stg_parts.sql`. Added DISTINCT to the select to remove exact duplicate rows that were causing the unique_stg_parts_part_key check to fail. This preserves the original column names and types while ensuring each part_key appears only once.

```diff
--- a/models/staging/stg_parts.sql
+++ b/models/staging/stg_parts.sql
@@ -1,4 +1,4 @@
-select
+select distinct
     p_partkey as part_key,
     p_name as part_name,
     p_brand as brand,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix correctly removes exact duplicate rows causing the unique key check to fail without masking data or altering logic.
