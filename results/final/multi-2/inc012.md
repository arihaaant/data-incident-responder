# Incident inc012

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `model.tpch_warehouse.stg_orders` error: Compilation Error in model stg_orders (models/staging/stg_orders.sql)

## Diagnosis

- **Started at:** `model.stg_orders`
- **Cause:** a change in a model
- **Downstream models affected:** `fct_daily_revenue`, `fct_orders`

**Evidence**

The stg_orders model selects o_orderdate as order_date without conversion, keeping it VARCHAR. The model's contract expects order_date as DATE, causing a compilation error. Profiling raw.orders.o_orderdate shows it is VARCHAR but can be losslessly converted to DATE using format %m/%d/%Y (15000 rows, 0 failures). Thus the issue is the model's SQL not applying the required cast, not upstream data. Updating the model to cast order_date (e.g., strptime(trim(o_orderdate), '%m/%d/%Y')::date) will satisfy the contract.

**Column profile** `raw.orders.o_orderdate` (varchar to date): converts without loss

## What was done

Proposed a change to `models/staging/stg_orders.sql`. Added explicit conversion for o_orderdate to match the contract's DATE type. Using strptime with the detected format %m/%d/%Y and trimming whitespace ensures lossless conversion. All other columns and types remain unchanged, preserving the original model structure.

```diff
--- a/models/staging/stg_orders.sql
+++ b/models/staging/stg_orders.sql
@@ -3,7 +3,7 @@
     o_custkey as customer_key,
     o_orderstatus as order_status,
     o_totalprice as total_price,
-    o_orderdate as order_date,
+    strptime(trim(o_orderdate), '%m/%d/%Y')::date as order_date,
     o_orderpriority as priority,
     _loaded_at as loaded_at
 from {{ source('raw', 'orders') }}
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix correctly casts o_orderdate to DATE using lossless format %m/%d/%Y as indicated by profile; addresses root cause without masking data.
