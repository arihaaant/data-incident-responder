# Incident inc038

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_customers_customer_key` fail (225 rows): Got 225 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.customer`, column `c_custkey`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `dim_customers`, `fct_daily_revenue`, `fct_orders`, `stg_customers`

**Evidence**

stg_customers selects c_custkey as customer_key directly from raw.customer. raw.customer has 1500 distinct c_custkey but 1725 total rows, with 225 duplicate keys (e.g., c_custkey=6 appears twice with identical column values). The uniqueness test on stg_customers.customer_key fails with 225 duplicate rows. Since duplicates are identical, policy dictates deduplication in staging model as a patch.

## What was done

Proposed a change to `models/staging/stg_customers.sql`. Added a CTE to reference the raw source and applied SELECT DISTINCT across all columns. This removes the 225 duplicate rows where the entire record is identical, satisfying the uniqueness test on `customer_key` while preserving column names and types.

```diff
--- a/models/staging/stg_customers.sql
+++ b/models/staging/stg_customers.sql
@@ -1,4 +1,9 @@
-select
+with source as (
+    select *
+    from {{ source('raw', 'customer') }}
+)
+
+select distinct
     c_custkey as customer_key,
     c_name as customer_name,
     c_address as address,
@@ -6,4 +11,4 @@
     c_nationkey as nation_key,
     c_mktsegment as market_segment,
     c_acctbal as account_balance
-from {{ source('raw', 'customer') }}
+from source
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix correctly deduplicates identical rows using SELECT DISTINCT, addressing the upstream duplicate key issue without masking data or altering schema.
