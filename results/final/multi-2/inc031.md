# Incident inc031

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_orders_order_key` fail (300 rows): Got 300 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.orders`, column `o_orderkey`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_orders`, `stg_orders`

**Evidence**

raw.orders contains duplicate rows for many order_key values (e.g., o_orderkey=800 appears twice with identical column values). stg_orders selects directly from raw.orders without deduplication, causing unique_stg_orders_order_key check to fail with 300 duplicate rows.

## What was done

Proposed a change to `models/staging/stg_orders.sql`. The raw.orders source contains exact duplicate rows (same order_key and all other column values). The staging model stg_orders previously selected rows directly, causing the unique_stg_orders_order_key check to fail with 300 duplicate order_key values. By adding SELECT DISTINCT we remove these exact duplicate rows while preserving the original column names and data types, satisfying the uniqueness check without altering any non-duplicate data.

```diff
--- a/models/staging/stg_orders.sql
+++ b/models/staging/stg_orders.sql
@@ -1,4 +1,5 @@
 select
+    distinct
     o_orderkey as order_key,
     o_custkey as customer_key,
     o_orderstatus as order_status,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix adds SELECT DISTINCT to remove exact duplicate rows, directly addressing the duplicate order_key issue without masking data or altering non-duplicate rows.
