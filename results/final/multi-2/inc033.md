# Incident inc033

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_orders_order_key` fail (3000 rows): Got 3000 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.orders`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_orders`, `stg_orders`

**Evidence**

raw.orders has 18,000 rows but only 15,000 distinct o_orderkey; duplicate rows (e.g., o_orderkey 358 appears twice with identical column values). stg_orders selects directly from raw.orders, so duplicate primary keys propagate, causing unique_stg_orders_order_key check to fail with 3,000 duplicates. Duplicates are exact matches, indicating batch delivered twice; policy allows deduplication in staging model.

## What was done

Proposed a change to `models/staging/stg_orders.sql`. Added a deduplication step to remove exact duplicate rows that were caused by a batch being delivered twice. The inner query assigns a row number per `o_orderkey` ordered by the most recent `_loaded_at`. The outer query filters to keep only the first row per key, preserving the original column list and data types while ensuring the `order_key` is unique, which resolves the failing `unique_stg_orders_order_key` check.

```diff
--- a/models/staging/stg_orders.sql
+++ b/models/staging/stg_orders.sql
@@ -6,4 +6,10 @@
     o_orderdate as order_date,
     o_orderpriority as priority,
     _loaded_at as loaded_at
-from {{ source('raw', 'orders') }}
+from (
+    select
+        *,
+        row_number() over (partition by o_orderkey order by _loaded_at desc) as _rn
+    from {{ source('raw', 'orders') }}
+) as sub
+where _rn = 1
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix correctly deduplicates exact duplicate rows caused by double batch load, preserving data integrity and satisfying unique key check. No masking, no type changes, and aligns with policy allowing deduplication in staging.
