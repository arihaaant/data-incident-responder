**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_fct_orders_order_key` fail (12900 rows): Got 12900 results, configured to fail if != 0

## Diagnosis

- **Started at:** `model.fct_orders`
- **Cause:** a change in a model
- **Downstream models affected:** `fct_daily_revenue`

**Evidence**

raw.orders has 15000 rows distinct order_key; stg_orders also 15000 distinct; fct_order_items has 60175 rows (multiple items per order). fct_orders also 60175 rows but only 15000 distinct order_key, causing duplicate key check failure. The fct_orders model joins items aggregated by order_key and line_number, resulting in one row per line item. Removing line_number from GROUP BY will produce one row per order, fixing duplicates.

## What was done

Proposed a change to `models/marts/fct_orders.sql`. The duplicate key failure was caused by the items CTE grouping by both order_key and line_number, which produced one row per line item. By grouping only on order_key, we aggregate all items per order, ensuring a single row per order_key in fct_orders. This resolves the unique_fct_orders_order_key check while preserving all existing columns and types.

```diff
--- a/models/marts/fct_orders.sql
+++ b/models/marts/fct_orders.sql
@@ -5,7 +5,7 @@
         sum(extended_price) as gross_revenue,
         sum(net_revenue) as net_revenue
     from {{ ref('fct_order_items') }}
-    group by order_key, line_number
+    group by order_key
 )
 
 select
```

- **Reviewer:** approved. Fix correctly aggregates items per order by removing line_number from GROUP BY, eliminating duplicate order_key rows without masking data or altering column types.
