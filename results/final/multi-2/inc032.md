# Incident inc032

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_orders_order_key` fail (1200 rows): Got 1200 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.orders`, column `o_orderkey`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_orders`, `stg_orders`

**Evidence**

raw.orders has 16200 rows but only 15000 distinct o_orderkey values (1200 duplicate keys). Example key 1216 appears twice with identical column values, indicating duplicate rows in source. stg_orders selects directly from raw.orders, so duplicates flow downstream, causing unique_stg_orders_order_key check to fail. Duplicates are identical, so they can be deduplicated in the staging model (patch).

## What was done

Proposed a change to `models/staging/stg_orders.sql`. Added DISTINCT to remove the 1,200 duplicate rows (identical across all columns) that caused the unique_stg_orders_order_key check to fail. This preserves the original column names and types while ensuring each order_key appears only once.

```diff
--- a/models/staging/stg_orders.sql
+++ b/models/staging/stg_orders.sql
@@ -1,5 +1,5 @@
 select
-    o_orderkey as order_key,
+    distinct o_orderkey as order_key,
     o_custkey as customer_key,
     o_orderstatus as order_status,
     o_totalprice as total_price,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix correctly removes exact duplicate rows causing the unique key check to fail without masking data or altering semantics.
