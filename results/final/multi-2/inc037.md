# Incident inc037

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_customers_customer_key` fail (75 rows): Got 75 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.customer`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `dim_customers`, `fct_daily_revenue`, `fct_orders`, `stg_customers`

**Evidence**

raw.customer has 1575 rows but only 1500 distinct c_custkey values, indicating 75 duplicate primary key rows. The duplicates are identical across all columns (e.g., c_custkey 458 appears twice with identical data). The staging model stg_customers simply selects and renames c_custkey, so the duplicate keys propagate, causing the unique_stg_customers_customer_key check to fail with 75 duplicate rows. Policy: identical duplicates are a delivery duplication; fix by deduplicating in the staging model.

## What was done

Proposed a change to `models/staging/stg_customers.sql`. The raw.customer source contains 75 exact duplicate rows (same c_custkey and all other column values). The staging model stg_customers simply selected the source columns, propagating those duplicates, which caused the unique_stg_customers_customer_key check to fail. Since the duplicates are identical, they represent a delivery duplication and can be safely removed by deduplicating in the staging model. Using SELECT DISTINCT preserves the original column names and types while eliminating the duplicate rows, fixing the uniqueness check without altering any other logic.

```diff
--- a/models/staging/stg_customers.sql
+++ b/models/staging/stg_customers.sql
@@ -1,4 +1,4 @@
-select
+select distinct
     c_custkey as customer_key,
     c_name as customer_name,
     c_address as address,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix correctly removes exact duplicate rows using SELECT DISTINCT, addressing the delivery duplication root cause without masking or altering data.
