# Incident inc030

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `not_null_stg_lineitem_discount` fail (5419 rows): Got 5419 results, configured to fail if != 0

## Diagnosis

- **Started at:** `model.stg_lineitem`
- **Cause:** a change in a model
- **Downstream models affected:** `fct_daily_revenue`, `fct_order_items`, `fct_orders`

**Evidence**

raw.lineitem has 5,419 rows where l_discount = 0. stg_lineitem.sql uses case when l_discount > 0 then l_discount end, turning zero discounts into NULL, causing not_null test to fail. The upstream raw data is fine; the model logic is wrong.

<details><summary>2 queries run during the investigation</summary>

```sql
SELECT COUNT(*) AS total_rows, COUNT(*) FILTER (WHERE discount IS NULL) AS null_discount FROM raw.lineitem
```
```sql
SELECT COUNT(*) AS total, COUNT(*) FILTER (WHERE l_discount = 0) AS zero_discount, COUNT(*) FILTER (WHERE l_discount > 0) AS pos_discount FROM raw.lineitem
```

</details>

## What was done

Proposed a change to `models/staging/stg_lineitem.sql`. The not_null test on `discount` was failing because the model used `case when l_discount > 0 then l_discount end`, which turned legitimate zero discounts into NULL. Replaced the conditional with a direct reference to `l_discount`, preserving zero values and maintaining the original column type. All other columns and logic remain unchanged.

```diff
--- a/models/staging/stg_lineitem.sql
+++ b/models/staging/stg_lineitem.sql
@@ -6,7 +6,7 @@
     l_suppkey as supplier_key,
     l_quantity as quantity,
     l_extendedprice as extended_price,
-    case when l_discount > 0 then l_discount end as discount,
+    l_discount as discount,
     l_tax as tax,
     l_returnflag as return_flag,
     l_shipdate as ship_date,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix directly addresses root cause by preserving zero discounts; no data masking, type unchanged, and logic remains correct.
