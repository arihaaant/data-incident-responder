## What broke

- `unique_fct_orders_order_key` fail (12900 rows): Got 12900 results, configured to fail if != 0

## Diagnosis

- **Started at:** `model.fct_orders`
- **Cause:** a change in a model
- **Downstream models affected:** `fct_daily_revenue`

**Evidence**

raw.orders has 15000 rows distinct order_key; staging.stg_orders also 15000 distinct; fct_orders has 60175 rows but only 15000 distinct order_key, indicating duplication from join. items CTE groups by order_key, line_number, producing multiple rows per order, causing duplicate rows in fct_orders. Fix by grouping only by order_key (remove line_number) in fct_order_items aggregation.

## What was done

Proposed a change to `models/marts/fct_orders.sql`. Removed the erroneous grouping by line_number in the items CTE. The original query aggregated fct_order_items by both order_key and line_number, which produced multiple rows per order and caused duplicate order_key rows in fct_orders, violating the unique constraint. By grouping only on order_key, we correctly aggregate item counts and revenue per order, ensuring one row per order_key and restoring the uniqueness check.

```diff
--- a/models/marts/fct_orders.sql
+++ b/models/marts/fct_orders.sql
@@ -5,7 +5,7 @@
         sum(extended_price) as gross_revenue,
         sum(net_revenue) as net_revenue
     from {{ ref('fct_order_items') }}
-    group by order_key, line_number
+    group by order_key
 )
 
 select
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix removes erroneous line_number grouping, correctly aggregates per order_key and eliminates duplicate rows, directly addressing the root cause.
