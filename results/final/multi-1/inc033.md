# Incident inc033

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_orders_order_key` fail (3000 rows): Got 3000 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.orders`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_orders`, `stg_orders`

**Evidence**

raw.orders has 18000 rows but only 15000 distinct o_orderkey values, yielding 3000 duplicate rows. Duplicate groups (e.g., o_orderkey=1,1216) show identical values across all columns, confirming exact duplicate deliveries. Staging model stg_orders simply selects columns, so duplicates propagate, causing unique_stg_orders_order_key check to fail.

## What was done

Proposed a change to `models/staging/stg_orders.sql`. The upstream raw.orders table contains exact duplicate rows (same order_key and all other column values). The staging model previously selected rows verbatim, propagating duplicates and causing the unique_stg_orders_order_key check to fail (3000 duplicate rows). By using SELECT DISTINCT we remove these exact duplicate deliveries while preserving the original schema, column names, and data types. This resolves the uniqueness check without altering any other logic.

```diff
--- a/models/staging/stg_orders.sql
+++ b/models/staging/stg_orders.sql
@@ -1,4 +1,4 @@
-select
+select distinct
     o_orderkey as order_key,
     o_custkey as customer_key,
     o_orderstatus as order_status,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix removes exact duplicate rows from source, directly addressing the duplicate key issue without masking or altering data. Acceptable deduplication in staging.
