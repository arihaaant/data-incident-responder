# Incident inc036

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_lineitem_order_line_id` fail (14739 rows): Got 14739 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.lineitem`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_order_items`, `fct_orders`, `stg_lineitem`

**Evidence**

raw.lineitem has 74,914 rows but only 60,175 distinct order_line_id (l_orderkey||'-'||l_linenumber). Duplicate groups (e.g., orderkey 32 linenumber 3) have identical values across all columns, indicating exact duplicate rows delivered by source. The stg_lineitem model simply forwards these rows, causing unique check to fail with 14,739 duplicates. Since duplicates are identical, policy says deduplicate in staging (patch) while root remains raw.lineitem.

## What was done

Proposed a change to `models/staging/stg_lineitem.sql`. The source raw.lineitem contains exact duplicate rows (identical across all columns). The unique check on order_line_id fails because duplicates are forwarded unchanged by the staging model. Adding DISTINCT to the SELECT removes these exact duplicate rows while preserving the original column names and data types, satisfying the unique constraint without altering downstream expectations.

```diff
--- a/models/staging/stg_lineitem.sql
+++ b/models/staging/stg_lineitem.sql
@@ -1,4 +1,5 @@
 select
+    distinct
     l_orderkey || '-' || l_linenumber as order_line_id,
     l_orderkey as order_key,
     l_linenumber as line_number,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix correctly deduplicates exact duplicate rows in staging as policy permits; no type/format changes involved.
