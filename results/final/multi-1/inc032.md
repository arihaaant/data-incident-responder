# Incident inc032

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_orders_order_key` fail (1200 rows): Got 1200 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.orders`, column `o_orderkey`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_orders`, `stg_orders`

**Evidence**

raw.orders has 16200 rows but only 15000 distinct o_orderkey, showing 1200 duplicate rows. Sample duplicate key 1216 appears twice with identical column values. stg_orders simply selects from raw.orders, so duplicates flow downstream, causing unique_stg_orders_order_key check to fail with 1200 duplicates. Identical duplicates indicate batch delivered twice; policy: deduplicate in staging model (patch).

## What was done

Proposed a change to `models/staging/stg_orders.sql`. Added DISTINCT to the select list to drop exact duplicate rows that resulted from a redelivered batch. The column list, names, and types remain unchanged, satisfying the staging model's contract while ensuring the unique_stg_orders_order_key check passes.

```diff
--- a/models/staging/stg_orders.sql
+++ b/models/staging/stg_orders.sql
@@ -1,4 +1,5 @@
 select
+    distinct
     o_orderkey as order_key,
     o_custkey as customer_key,
     o_orderstatus as order_status,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix adds DISTINCT to remove exact duplicate rows, directly addressing the duplicate key issue identified in the diagnosis without altering data semantics or masking underlying problems.
