# Incident inc038

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_customers_customer_key` fail (225 rows): Got 225 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.customer`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `dim_customers`, `fct_daily_revenue`, `fct_orders`, `stg_customers`

**Evidence**

raw.customer has 1725 rows but only 1500 distinct c_custkey values; duplicate keys (e.g., c_custkey=6) appear twice with identical column values. stg_customers mirrors raw, so unique check fails with 225 duplicate rows. Duplicates are exact copies, indicating a double delivery; policy says deduplicate in staging.

## What was done

Proposed a change to `models/staging/stg_customers.sql`. Added DISTINCT to remove exact duplicate rows caused by a double delivery. This preserves column names and types while ensuring the unique check on customer_key passes.

```diff
--- a/models/staging/stg_customers.sql
+++ b/models/staging/stg_customers.sql
@@ -1,4 +1,5 @@
 select
+    distinct
     c_custkey as customer_key,
     c_name as customer_name,
     c_address as address,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix adds DISTINCT to remove exact duplicate rows from raw.customer, directly addressing the duplicate key issue as per policy. No type/format changes involved, and the solution does not mask data.
