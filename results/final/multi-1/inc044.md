## What broke

- `assert_daily_revenue_one_row_per_region` fail (3659 rows): Got 3659 results, configured to fail if != 0

## Diagnosis

- **Started at:** `model.fct_daily_revenue`
- **Cause:** a change in a model

**Evidence**

The test assert_daily_revenue_one_row_per_region expects a single row per region per day. fct_daily_revenue groups by order_date, region_name, priority, but does not select priority, creating duplicate rows for each priority value. This extra grouping column is the source of the duplicate rows, a code issue. Removing priority from the GROUP BY (or including it in SELECT and adjusting downstream) will fix the test.

## What was done

Proposed a change to `models/marts/fct_daily_revenue.sql`. Removed the extraneous `priority` column from the GROUP BY clause. The model previously grouped by `order_date, region_name, priority` but did not select `priority`, causing duplicate rows per region per day when multiple priority values existed. The test `assert_daily_revenue_one_row_per_region` expects a single row per region per day, so grouping only by `order_date` and `region_name` resolves the duplicate rows while preserving the original columns and types.

```diff
--- a/models/marts/fct_daily_revenue.sql
+++ b/models/marts/fct_daily_revenue.sql
@@ -4,4 +4,4 @@
     count(*) as orders,
     sum(net_revenue) as net_revenue
 from {{ ref('fct_orders') }}
-group by order_date, region_name, priority
+group by order_date, region_name
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix removes the extraneous grouping column that caused duplicate rows, directly addressing the code change root cause without masking data.
