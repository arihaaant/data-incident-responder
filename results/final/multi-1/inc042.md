## What broke

- `unique_dim_customers_customer_key` fail (1500 rows): Got 1500 results, configured to fail if != 0

## Diagnosis

- **Started at:** `model.dim_customers`
- **Cause:** a change in a model
- **Downstream models affected:** `fct_daily_revenue`, `fct_orders`

**Evidence**

stg_customers has 1500 rows, dim_customers has 7500 rows (5x). Join in dim_customers uses n.region_key = n.region_key, causing each customer to duplicate for each region. Fix join to n.region_key = r.region_key.

## What was done

Proposed a change to `models/marts/dim_customers.sql`. Fixed the join condition for the regions table. The original query incorrectly joined `stg_regions` on `n.region_key = n.region_key`, which is always true and caused a Cartesian product, inflating rows in `dim_customers`. Updated the condition to correctly match `n.region_key` to `r.region_key`, eliminating duplicate rows and allowing the unique_customer_key test to pass.

```diff
--- a/models/marts/dim_customers.sql
+++ b/models/marts/dim_customers.sql
@@ -7,4 +7,4 @@
     r.region_name
 from {{ ref('stg_customers') }} c
 join {{ ref('stg_nations') }} n on c.nation_key = n.nation_key
-join {{ ref('stg_regions') }} r on n.region_key = n.region_key
+join {{ ref('stg_regions') }} r on n.region_key = r.region_key
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix corrects the erroneous join condition causing row duplication. It addresses the root cause without masking data or altering column values.
