# Incident inc037

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_customers_customer_key` fail (75 rows): Got 75 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.customer`, column `c_custkey`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `dim_customers`, `fct_daily_revenue`, `fct_orders`, `stg_customers`

**Evidence**

raw.customer has 1575 rows but only 1500 distinct c_custkey values; 75 duplicate keys (e.g., c_custkey=16 appears twice with identical column values). stg_customers directly selects from raw.customer, so duplicates flow downstream, causing unique_stg_customers_customer_key check to fail. Duplicates are identical across all columns, indicating a double batch load, which can be resolved by deduplication in the staging model.

## What was done

Proposed a change to `models/staging/stg_customers.sql`. Added DISTINCT to the select to remove the 75 duplicate rows that have identical values across all columns. This resolves the unique_stg_customers_customer_key check failure while preserving column names and types.

```diff
--- a/models/staging/stg_customers.sql
+++ b/models/staging/stg_customers.sql
@@ -1,4 +1,4 @@
-select
+select distinct
     c_custkey as customer_key,
     c_name as customer_name,
     c_address as address,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix adds DISTINCT to remove exact duplicate rows, directly addressing the duplicate key issue identified in the diagnosis without masking data or altering logic.
