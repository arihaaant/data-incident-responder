# Incident inc031

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_orders_order_key` fail (300 rows): Got 300 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.orders`, column `o_orderkey`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_orders`, `stg_orders`

**Evidence**

Raw orders table has 30,300 rows but only 15,000 distinct order_key values; duplicate rows are exact copies (no column differences). Staging stg_orders mirrors raw row count and shows same duplicate order_key values, causing unique check to fail with 300 duplicate rows.

## What was done

Proposed a change to `models/staging/stg_orders.sql`. The raw orders table contains exact duplicate rows (same values across all columns) leading to 300 duplicate order_key values and a failing unique check. Since the duplicates are identical, we can safely deduplicate by selecting distinct rows. This preserves the original column names and types while removing the duplicate rows, allowing the unique_stg_orders_order_key check to pass.

```diff
--- a/models/staging/stg_orders.sql
+++ b/models/staging/stg_orders.sql
@@ -1,4 +1,5 @@
 select
+    distinct
     o_orderkey as order_key,
     o_custkey as customer_key,
     o_orderstatus as order_status,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix removes exact duplicate rows, directly addressing duplicate order_key issue without masking data or altering columns. Acceptable deduplication.
