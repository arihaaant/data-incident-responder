# Incident inc035

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_lineitem_order_line_id` fail (5639 rows): Got 5639 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.lineitem`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_order_items`, `fct_orders`, `stg_lineitem`

**Evidence**

raw.lineitem has 65,814 rows but only 60,175 distinct order_line_id (orderkey-linenumber). Example duplicate rows for orderkey=164 linenumber=5 are identical across all columns, indicating batch delivered twice. The unique test on stg_lineitem.order_line_id fails with 5,639 duplicates, which originates from these raw duplicates.

## What was done

Proposed a change to `models/staging/stg_lineitem.sql`. The raw lineitem source contains exact duplicate rows caused by a batch being delivered twice, leading to 5,639 duplicate order_line_id values and a failing unique test. Since the duplicates are identical across all columns, we can safely deduplicate by adding SELECT DISTINCT. This removes the redundant rows without altering column names, types, or any business logic, allowing the unique test on order_line_id to pass.

```diff
--- a/models/staging/stg_lineitem.sql
+++ b/models/staging/stg_lineitem.sql
@@ -1,4 +1,5 @@
 select
+    distinct
     l_orderkey || '-' || l_linenumber as order_line_id,
     l_orderkey as order_key,
     l_linenumber as line_number,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. The fix adds SELECT DISTINCT to remove exact duplicate rows, which does not alter data semantics and resolves the unique test failure. Duplicates are identical across all columns, so deduplication is safe and not masking non‑duplicate data.
