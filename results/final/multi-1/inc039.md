# Incident inc039

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `unique_stg_parts_part_key` fail (200 rows): Got 200 results, configured to fail if != 0

## Diagnosis

- **Started at:** `source.raw.part`, column `p_partkey`
- **Cause:** data arriving from upstream
- **Downstream models affected:** `fct_daily_revenue`, `fct_order_items`, `fct_orders`, `stg_parts`

**Evidence**

raw.part has 2200 rows but only 2000 distinct p_partkey values, indicating 200 duplicate primary key rows. Query grouping by p_partkey shows each duplicate has identical values across all columns (name_cnt, mfgr_cnt, brand_cnt, type_cnt, price_cnt, comment_cnt all = 1). The stg_parts model selects p_partkey as part_key without deduplication, so duplicates flow downstream, causing the unique_stg_parts_part_key check to fail with 200 rows. Duplicates are exact copies, so per policy they should be deduplicated in the staging model (patch).

## What was done

Proposed a change to `models/staging/stg_parts.sql`. The raw `part` source contains 200 exact duplicate rows (same values for all columns). The staging model `stg_parts` previously selected rows directly, allowing duplicates to flow downstream and causing the `unique_stg_parts_part_key` check to fail. Adding `DISTINCT` removes these exact duplicate rows while preserving the original column names and data types, satisfying the uniqueness check without altering any other logic.

```diff
--- a/models/staging/stg_parts.sql
+++ b/models/staging/stg_parts.sql
@@ -1,4 +1,5 @@
 select
+    distinct
     p_partkey as part_key,
     p_name as part_name,
     p_brand as brand,
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Patch correctly deduplicates exact duplicate rows using DISTINCT, addressing the root cause without masking data or altering logic.
