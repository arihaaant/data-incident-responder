# Incident inc027

**Status:** Fix proposed. Needs a human review before it is merged.

## What broke

- `not_null_stg_customers_market_segment` fail (288 rows): Got 288 results, configured to fail if != 0

## Diagnosis

- **Started at:** `model.stg_customers`
- **Cause:** a change in a model
- **Downstream models affected:** `dim_customers`, `fct_daily_revenue`, `fct_orders`

**Evidence**

stg_customers view (1500 rows) has 288 null market_segment values, while raw.customer has 0 null c_mktsegment. Model SQL uses nullif(trim(c_mktsegment), 'MACHINERY') which turns 'MACHINERY' values into NULL. Query shows exactly 288 rows where c_mktsegment = 'MACHINERY', matching the null count. Therefore the nulls are introduced by the model logic, not upstream data. Fix by removing or correcting the nullif expression.

## What was done

Proposed a change to `models/staging/stg_customers.sql`. Removed the nullif() that was converting 'MACHINERY' values to NULL, which caused 288 null market_segment values and failed the not_null check. Now we simply trim the source value, preserving all original market segment strings, including 'MACHINERY'. This keeps the column name and type unchanged.

```diff
--- a/models/staging/stg_customers.sql
+++ b/models/staging/stg_customers.sql
@@ -4,6 +4,6 @@
     c_address as address,
     c_phone as phone,
     c_nationkey as nation_key,
-    nullif(trim(c_mktsegment), 'MACHINERY') as market_segment,
+    trim(c_mktsegment) as market_segment,
     c_acctbal as account_balance
 from {{ source('raw', 'customer') }}
```

- **Tested in a copy of the warehouse:** every check passed.
- **Reviewer:** approved. Fix correctly removes the nullif that introduced nulls, preserving original market_segment values. No masking, no data loss, and aligns with root cause.
